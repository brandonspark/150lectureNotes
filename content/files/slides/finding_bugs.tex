\begin{frame}[fragile]
  \frametitle{Why are we here?}

  The finest of parkour runners know the importance of guardrails.

  \pause
  \vspace{\fill}

  Here at OWASP AppSec Days PNW, we are no different. In the absence of
  \term{secure guardrails}, the only difference between a parkour runner and a
  security engineer is in the time elapsed to hit the ground.\footnote{He survived.}

  \pause
  \vspace{\fill}

  \defBox{}{The idea of \term{secure guardrails} is in making security the
  \textbf{default} behavior, rather than something that is \textbf{opted into}.
  In the lifecycle of software development, it champions guiding
  developers into secure practices \textbf{early}, rather than chasing down
  vulnerabilities once they have already occurred.
  }
\end{frame}

\sectionSlide{2}{Static Analysis Essentials}

\begin{frame}[fragile]
  \frametitle{Software and security}

  We're here because we are interested in \term{software security}.

  \pause
  \vspace{5pt}

  Broadly, we are interested in categories of undesirable behaviors in programs, and
  in particular, we are interested in minimizing them wherever possible. These may
  take the form of:

  \pause
  \vspace{5pt}

  \begin{itemize}
    \item \textbf{logic errors} - passing an ill-typed argument to a function
    \pause
    \item \textbf{code smells} - using a deprecated utility function instead of a more
    up-to-date one
    \pause
    \item \textbf{security vulnerabilities} - SQL injection, cross-site scripting, broken authentication
  \end{itemize}

  \pause
  \vspace{5pt}

  All of these are fair game for things that we want to find and fix. Our weapon of
  choice for doing so is \term{static analysis}.
\end{frame}

\begin{frame}[fragile]
  \frametitle{What is static analysis?}

  \defBox{}{\term{Static analysis} is the art of analyzing programs without ever running them.}

  \pause
  \vspace{5pt}

  This is in contrast to \term{dynamic analysis}, which involves running the program and observing
  its behavior at runtime. While an interesting field in its own right, dynamic analysis
  has its own disadvantages, so it is out of scope for this workshop.

  \pause
  \vspace{\fill}

  You may think of the difference between static analysis and dynamic analysis by analogy to
  the problem of trying to ascertain if a gun is faulty.

  \pause
  \vspace{\fill}

  Static analysis would be checking the gun for defects by taking it apart and examining its
  mechanical structure.

  \pause
  \vspace{5pt}

  Dynamic analysis would be firing the gun and observing if it explodes in your hand.
  \footnote{This is only slightly a misrepresentation, but the problem is that a gun not exploding \textit{now}
  does not mean it will not explode \textit{later}.}
\end{frame}

\begin{frame}[fragile]
  \frametitle{Goals in Static Analysis}

  Static analysis should be:

  \pause
  \vspace{5pt}

  \begin{enumerate}
      \item \textbf{fast} - Scanning code with a static analysis solution should run
      quickly, so that developers can get feedback and iterate as quickly as possible.
      \footnote{The car's moving at 90mph. It's not going to wait for you to lay down some brickwork.}
      \pause
      \item \textbf{fitting} - Static analysis should be customized to \textit{your}
      use case. Teams, codebases, and organizations are \textit{not} one-size-fits-all.
      You should be able to scan your code in a \textbf{way that works for you}.
      \pause
      \item \textbf{friendly} - Static analysis tools should be simple to use, for
      both developers and security engineers. A tool which is not understood is a tool
      which will be disabled.
  \end{enumerate}

  \pause
  \vspace{\fill}

  These are all things that Semgrep aims to achieve.
\end{frame}

\sectionSlide{3}{Basics: Conceptual Fundamentals}

\begin{frame}[fragile]
  \frametitle{The Semgrep Pipeline}

  Here's some things about Semgrep that are cool:

  \pause

  \begin{itemize}
    \item {\color{auxColor}\faBookOpen} \, \textbf{open-source}, with community-contributed language support and rules
    \pause
    \item {\color{auxColor}\faPen} \, \textbf{customizable} - Semgrep scans for code patterns that you define, and provide
    as an argument to the tool. This means that Semgrep can be customized to your code
    base's idioms, and tuned to your organization's security needs.
    \pause
    \item {\color{auxColor}\faFont} \, \textbf{multilingual} - Semgrep supports over 25+ languages
    \pause
    \item {\color{auxColor}\faTimes} \, \textbf{no building required}. Semgrep only needs source code to run, and doesn't
    require that the code it is analyzing can build
    \pause
    \item {\color{auxColor}\faLightbulb} \, \textbf{No DSL}. Semgrep patterns look like code in the language you're targeting,
    meaning no hours of browsing documentation and API references. All you need to be able
    to do is read and write code.\footnote{This is really a killer, and will form the basis
    of this workshop as we move into Semgrep rule-writing.}
  \end{itemize}
\end{frame}

\begin{frame}[fragile]
  \frametitle{Example: A search problem}

  Semgrep is about \textbf{matching nodes} and \textbf{obtaining ranges}.

  \pause
  \vspace{\fill}

  Suppose we were interested in matching calls to \code{print} in Python. We could
  be concerned with the following program:

  \vspace{5pt}

  \begin{pythoncodeblock}
    # this line will print
    print("Hello, world!")

    isprinted(True)

    print("printing")
  \end{pythoncodeblock}

  \pause
  \vspace{\fill}

  We could use \code{grep} or \code{ctrl-f} to find these calls, but they won't
  work properly!
\end{frame}


\begin{frame}[fragile]
  \frametitle{A syntactic \code{grep}}

  By \code{grep}ping for \code{print}, we would get the following:

  \pause
  \vspace{5pt}

  % FRAGILE
  \begin{codeblock}
    # this line will |lr|print|lr|
    |lr|print|lr|('Hello, world!')

    is|lr|print|lr|ed(True)

    |lr|print|lr|('|lr|print|lr|ing now')
  \end{codeblock}

  \pause
  \vspace{\fill}

  We were interested in finding \textbf{calls} to \code{print}. We see
  that we have three matches we didn't intend -- three \term{false positives}.

  \pause
  \vspace{\fill}

  The reason is that \code{grep} is not aware of whether each contiguous \code{print}
  is a call or not. It just operates purely based on characters. Put another way,
  \code{grep} is not \term{semantic}.
\end{frame}

\begin{frame}[fragile]
  \frametitle{A semantic \code{grep}}

  Semgrep stands for \term{semantic grep}. It is a code-searching tool that is aware
  of the underlying structure of the code -- that is, the AST.

  \pause
  \vspace{\fill}

  Consider the following example:

  \vspace{5pt}

__compare(
<<<
  print
>>>,
<<<
    # this line will print
    print("Hello, world!")
    isprinted(True)
    print("printing")
>>>
)
\end{frame}

\begin{frame}[fragile]
  \frametitle{A semantic \code{grep}}

  With Semgrep, we will match the two calls to \code{print}, and nothing else.

  \vspace{\fill}

__compare(
<<<
  print
>>>,
<<<
    # this line will print
    `print`("Hello, world!")
    isprinted(True)
    `print`("printing")
>>>
)

  \pause
  \vspace{\fill}

  Note that it is not simply a matter of ignoring the comments and string literals -- we
  also do not match the identifier \code{isprinted}, because it is not the same as the
  identifier \code{print}.
\end{frame}

\begin{frame}[fragile]

\begin{frame}[fragile]
  \frametitle{Ellipses}

  To do this, we will need to somehow vary our pattern over any argument to the
  call. We do this with a special Semgrep syntax, the \term{ellipsis}.

  \pause
  \vspace{\fill}

  \customBox{Feature}{\, The \term{ellipsis} is a placeholder in a Semgrep pattern which matches
    zero or more occurrences of some element, for instance parameters, arguments,
    and statements.
  }

  \pause
  \vspace{\fill}

__compare_30(
<<<
  print(...)
>>>,
<<<
  # this code should be matched...
  `print("a call to print")`

  alias = print
>>>
)

  \pause
  \vspace{\fill}

  \noteBox{}{The range has changed! Instead of matching just the identifier \code{print},
  our match now covers the entire call.}
\end{frame}

\begin{frame}[fragile]
  \frametitle{Ellipsis Isn't Magic}

  Something I feel that I must get across to you, that people often get wrong, is that
  \textbf{the ellipsis is not magic}.\footnote{Friendship is, though.} Consider the following pattern:

  \pause
  \vspace{\fill}
  __pattern(
<<<
  def ...
>>>
  )

  \pause
  \vspace{\fill}

  This looks like it should match any function definition, because we match a \code{def},
  and then a sequence of things, which would match a function like:

  \vspace{\fill}

  \begin{pythoncodeblock}
    def foo():
      return
  \end{pythoncodeblock}

  \pause
  \vspace{\fill}

  Unfortunately, this isn't how Semgrep works at all, and will result in a pattern parse error.
\end{frame}

\begin{frame}[fragile]
  \frametitle{Ellipsis Isn't Magic}

  In most cases, an ellipsis is \textbf{only admissible} wherever you could put a sequence
  of parameters, arguments, or statements.

  \pause
  \vspace{\fill}

  Some might be tempted to think of it like \code{.*} in regex, but it's not the same! Recall
  that patterns are \textit{parsed}, meaning that Semgrep patterns must \textit{look like code}
  in the language they are a part of.

  \pause
  \vspace{\fill}

  What Python construct looks like \code{def ...}, where \code{...} is a sequence of arguments,
  parameters, or statements? The answer is \textbf{none}, and so the pattern is invalid.

  \pause
  \vspace{\fill}

  Above all else, remember: \term{patterns must parse}!
\end{frame}



\begin{frame}[fragile]
  \frametitle{Metavariables}

  Sometimes, we are only interested in functions with just a single argument, though.

  In these cases, ellipsis is too permissive.

  \pause
  \vspace{\fill}

  We need a construct which denotes a single element in the program, kind of like
  a placeholder. We will call this a \term{metavariable}.\footnote{It's like a regular
  variable, but it drinks and goes to parties.}

  \pause
  \vspace{\fill}

  \customBox{Feature}{\, The \term{metavariable} is a placeholder in a Semgrep
    pattern which matches exactly one occurrence of some element, for instance
    an argument, expression, or identifier.
  }

  \pause
  \vspace{\fill}

  The syntax for a metavariable is a dollar sign prefixing a capital identifier,
  for instance \code{$\dollar$X} or \code{$\dollar$EXPR}. Usually, you can put
  it anywhere in a pattern that you could ordinarily put an identifier.
\end{frame}

\begin{frame}[fragile]

\begin{frame}[fragile]
  \frametitle{Combining patterns}

  Sometimes, when we are trying to match something, we are interested in combining
  multiple matches in some way.

  \pause
  \vspace{\fill}

  Usually, this we want to match something which is \textbf{one of
  several things}, or \textbf{all of several things}.

  \pause
  \vspace{\fill}

  \customBox{Feature}{\, The \code{all} and \code{any} operators are patterns which
  combine other patterns. \code{all} matches ranges where all of the children patterns
  match, and \code{any} matches ranges where at least one of the children patterns match.}

  \pause
  \vspace{\fill}

__rule(
<<<
    any:
      - "exec(...)"
      - "print(...)"
>>>)

  \pause
  \vspace{\fill}

  This pattern matches \textbf{both} calls to \code{exec} and calls to \code{print}.
\end{frame}

\begin{frame}[fragile]
  \frametitle{The \code{any} pattern}

  \code{any} operates under \term{set union} rules, where each of its children produces a
  set of matches, which are simply unioned together.

  \pause
  \vspace{\fill}


{\small
__compare_rule(
<<<
any:
  - |fb|"exec(...)"|fb|
  - |fr|"print(...)"|fr|
>>>,
<<<
|fb|exec("ls")|fb|
|fr|print("hi")|fr|
>>>
)
}


  \pause
  \vspace{\fill}

  \begin{center}
    \{ \tikz[inline] \node[box, fill=hlFaintBlue, minimum width=0.4cm, minimum height=0.4cm, yshift=0.145cm]{}; \}
    $\cup$ \{ \tikz[inline] \node[box, fill=hlFaintRed, minimum width=0.4cm, minimum height=0.4cm, yshift=0.145cm]{}; \} =
    \{ \tikz[inline] \node[box, fill=hlFaintBlue, minimum width=0.4cm, minimum height=0.4cm, yshift=0.145cm]{};,
      \tikz[inline] \node[box, fill=hlFaintRed, minimum width=0.4cm, minimum height=0.4cm, yshift=0.145cm]{}; \}
    $\implies$ \textbf{2 matches}
  \end{center}

  \pause
  \vspace{\fill}

{\small
__compare_rule(
<<<
any:
  - |fb|"exec(...)"|fb|
  - |fr|"print(...)"|fr|
>>>,
<<<
`exec("ls")`
`print("hi")`
>>>
)
}
\end{frame}

\begin{frame}[fragile]
  \frametitle{The \code{all} pattern}

  \code{all}, on the other hand, operates under \term{set intersection} rules
  (or similar to it), where each of its ranges are intersected with each other,
  keeping the smaller ones.

  \pause
  \vspace{\fill}

{\small
__compare_rule(
<<<
  all:
    - |fb|"exec(...)"|fb|
    - |fr|"print(...)"|fr|
>>>,
<<<
  |fb|exec("ls")|fb|
  |fr|print("hi")|fr|
>>>
)
}

  \pause
  \vspace{\fill}

  \begin{center}
    \{ \tikz[inline] \node[box, fill=hlFaintBlue, minimum width=0.4cm, minimum height=0.4cm, yshift=0.145cm]{}; \}
    $\cap$ \{ \tikz[inline] \node[box, fill=hlFaintRed, minimum width=0.4cm, minimum height=0.4cm, yshift=0.145cm]{}; \} =
    \{  \} $\implies$ \textbf{no matches}
  \end{center}

  \pause
  \vspace{\fill}

{\small
__compare_rule(
<<<
all:
  - "exec(...)"
  - "print(...)"
>>>,
<<<
exec("ls")
print("hi")
>>>
)
}

  \pause
  \vspace{\fill}

  So we could write the above rule, but it's not very useful -- \textbf{it will
  match nothing}, because there is no way for a range to be both a call to
  \code{exec} \textit{and} a call to \code{print}.
\end{frame}

\begin{frame}[fragile]
  \frametitle{The \code{not} operator}

  Instead, the \code{all} operator is most useful when combined with \code{not}.

  \pause
  \vspace{\fill}

  \customBox{Feature}{\, The \code{not} operator, when placed under an \code{all}, means
  the result should be anything which \textit{does not} match the pattern under the
  \code{not}.}

  \pause
  \vspace{\fill}

  With this, we can express complementary logic, such as "all calls which are not
  the print function".

__compare_rule(
<<<
  all:
    - $FUNC(...)
    - not: print(...)
>>>,
<<<
  print("hi")
  `foo()`
  `exec("ls")`
>>>
)
  __useless($)
\end{frame}

\begin{frame}[fragile]
  \frametitle{The \code{inside} operator}

  So far, we have discussed four pattern operators in \code{pattern}, \code{not},
  \code{all}, and \code{any}.

\begin{frame}[fragile]
  \frametitle{Modifying ranges}

  Now that we've seen all the fundamental pattern operators, we can move on to
  \term{conditions} and \term{focusing}, which let us alter and constrain
  existing ranges.

  \pause
  \vspace{\fill}

  Sometimes we don't care about just producing a match, we care about the specific
  range that the match covers. For instance, we may want to match the name of a

)

\begin{frame}[fragile]
  \frametitle{Filtering matches via metavariables}

  Sometimes we want to constrain our matches to only ones which fulfill some conditions.
  Usually this is based on specific parts of the pattern, such as metavariables.

  \pause
  \vspace{\fill}

  \customBox{Feature}{\, \term{Metavariable conditions} are conditions that may be
  placed on a pattern, which filter out matches whose metavariables do not fulfill
  the condition. They come in three varieties:}
  \pause
  \begin{itemize}
    \item metavariable \code{pattern} constraints, which specify that a metavariable
    must contain a specified pattern inside of it
    \pause
    \item metavariable \code{regex} constraints, which specify that a metavariable
    must match a specific regex
    \pause
    \item metavariable \code{analyzer}s, which are specific kinds of validators
    that check for things such as high-entropy strings and ReDoS regexes
    \pause
    \item metavariable \code{type} constraints, which specify that a metavariable
    can only match expressions with a certain type
  \end{itemize}
\end{frame}

\sectionSlide{7}{Advanced: Taint Mode}

\begin{frame}[fragile]
  \frametitle{From search to taint}

  Many of the problems in security are not quite so simple as can be phrased in
  a regular search mode rule.

  \pause
  \vspace{\fill}

  Many problems in security come from the simple idea of sensitive data reaching
  a sensitive area, such as a network call or a file write. This problem is solvable
  via a classic technique in static analysis called \term{dataflow analysis}.

  \pause
  \vspace{\fill}

  \defBox{}{\term{Taint analysis} is a form of dataflow analysis which tracks whether
  some specified form of data (called the {\color{sourceColor}source}) is capable of reaching some
  specified sensitive site (called the {\color{sinkColor}sink}). We say that data which comes
  from the source is \term{tainted}.}
\end{frame}

\begin{frame}[fragile]
  \frametitle{Example: Dataflow analysis}

  For instance, consider the following code snippet:

  \begin{pythoncodeblock}[language=java]
    public class DataflowExample {
      public static void main(String |fb|args|fb|[]) throws IOException {
        String cmd = args[0];
        Runtime.getRuntime().exec(cmd);
      }
    }
  \end{pythoncodeblock}

  \pause
  \vspace{\fill}

  In this example, the input \code{args} to the program are a potential
  {\color{sourceColor}source} of user input, which is sensitive data!

  \pause
  \vspace{\fill}

  If this user input is allowed to reach the \code{Runtime.exec} method, for instance,
  an attacker could potentially cause dangerous arbitrary code execution.

  \pause
  \vspace{\fill}

  \begin{itemize}
    \item common sources: URL parameters, cookies, user input
    \item common sinks: SQL queries, shell commands
  \end{itemize}
\end{frame}

  \end{minipage}
  \begin{minipage}[t][1in][t]{\textwidth}
    \small
    That's a finding!

    \pause
    \vspace{5pt}

    This reflects exactly how Semgrep works in taint mode:
    \begin{enumerate}
      \setlength\itemsep{-0.15em}
      \pause
      \item {\color{sourceColor}sources} of tainted data are specified via patterns
      \pause
      \item {\color{sinkColor}sinks} of dangerous sites are specified via patterns
      \pause
      \item if a {\color{sourceColor}source} is able to taint data which reaches a {\color{sinkColor}sink}, a finding is produced at the sink
    \end{enumerate}
  \end{minipage}
\end{frame}

\begin{frame}[fragile]
  \frametitle{Example: Sanitized dataflow analysis}

    Let's look at another example:

    \begin{pythoncodeblock}[language=java]
      public class DataflowExample {

        }
      }

    The difference is that on the path to the sink, it goes through a function \code{filterFilePath},
    which verifies that the input is \textit{not} dangerous.

    \pause
    \vspace{\fill}

    \textbf{This means that the call to \code{exec} is safe here, and should not produce a finding!}

\sectionSlide{8}{Advanced: Autofix}

\begin{frame}[fragile]
  \frametitle{Friendly guardrails}

  We now know how to write Semgrep rules to match patterns, but that is only one piece
  of the puzzle. Being able to \textit{match} something doesn't necessarily tell you
  what you can \textit{do} with it.

  \pause
  \vspace{\fill}

  Remediation is a whole other half of the battle. How can we not just provide a
  guardrail around a dangerous behavior, but also tell developers what to do
  instead? We don't just build a guardrail to block others, we want to build a
  guardrail which will actively steer them towards better outcomes.

  % TODO: bouncy guardrail, rubber guardrail

  \pause
  \vspace{\fill}

  \customBox{Feature}{\, \term{Autofix} is a Semgrep feature that allows you to write patterns that
  replace the matched code with safe, remediated code.}

  \pause
  \vspace{\fill}

  Luckily, it's as easy as adding onto the Semgrep rules we've already learned to write!
\end{frame}

\begin{frame}[fragile]
  \frametitle{UI: How to add an autofix}

  To add an autofix to your rule, simply click the "Add fix" button located below the
  rule message in the rule info panel, and enter your autofix.

  \pause
  \vspace{\fill}

  \begin{center}
    \includegraphics[width=0.8\textwidth]{fix.png}
  \end{center}

  \pause
  \vspace{\fill}

  \noteBox{}{While autofixes are strictly textual, they are \term{interpolated}, meaning
  that metavariables appearing in them will be substituted for their matches. This allows
  you to refactor code based on what was there before!}
\end{frame}

\begin{frame}[fragile]
  \frametitle{Example: Autofix}

{\small
__compare_rule_35(
<<<
  pattern:
    print($STR)
  fix: |
    logger.info($STR)
>>>,
<<<
  |fr|print("hi")|fr||fg|logger.info("hi")|fg|
  |fr|print("there")|fr||fg|logger.info("there")|fg|
>>>
)
}

  \pause
  \vspace{\fill}

  Here, we see that the metavariable \code[mathescape=false]{$STR} is shared between the two,
  so while the \code{print} is replaced, the content inside of the call is the same.
  __useless($)

  \pause
  \vspace{\fill}

  \customBox{Fact}{\, Rules with autofixes have 50\% higher fix rate than rules without autofix.}
\end{frame}

  Congratulations, you've braved the wilds and written your first Semgrep rules!

  We've covered a lot of ground, but there's still more to learn. Semgrep is an

  Semgrep rules.
